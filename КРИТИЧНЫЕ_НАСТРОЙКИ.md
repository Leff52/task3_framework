# Критичные настройки и раннее обнаружение ошибок конфигурации

## Введение

Практическое занятие №3 демонстрирует критическую важность **валидации конфигурации перед запуском** приложения. Это не просто чтение параметров, а активная защита от случайных ошибок администратора, которые могут открыть приложение для атак.

## Критичные настройки

### 1. `TrustedOrigins` - Список доверенных источников

**Почему это критично:**
- Это единственное препятствие для CORS атак (Cross-Origin Request Forgery)
- Пустой список означает, что приложение открыто для запросов с любых источников
- Это создаёт уязвимость для украденных cookies, CSRF токенов и других данных браузера

**Валидация в коде:**

**C#** (`AppOptionsValidator.cs`):
```csharp
if (options.TrustedOrigins.Length == 0)
    errors.Add("Список доверенных источников пуст, служба не может быть открыта без ограничений");

foreach (var origin in options.TrustedOrigins)
{
    if (!Uri.TryCreate(origin, UriKind.Absolute, out var uri))
    {
        errors.Add($"Доверенный источник задан неверно, значение {origin}");
        continue;
    }
    if (uri.Scheme is not ("http" or "https"))
        errors.Add($"Доверенный источник должен иметь схему http или https");
}
```

**Node.js** (`config.js`):
```javascript
if (origins.length === 0) {
    errors.push("Список доверенных источников пуст...");
}
```

**Как это происходит:**
1. Приложение **не запустится**, если список пуст
2. Администратор увидит четкое сообщение об ошибке
3. Это предотвращает развёртывание незащищённого приложения

### 2. `ReadPerMinute` и `WritePerMinute` - Лимиты частоты запросов

**Почему это критично:**
- Без лимитов single attacker может заполнить CPU/память приложения
- Это защита от DDoS атак и brute-force попыток
- Слишком низкий лимит заблокирует легитимных пользователей
- Лимит записи `WritePerMinute` не должен превосходить `ReadPerMinute` (логически)

**Валидация в коде:**

**C#**:
```csharp
if (options.RateLimits.ReadPerMinute <= 0)
    errors.Add("Лимит чтения должен быть больше нуля");
if (options.RateLimits.WritePerMinute > options.RateLimits.ReadPerMinute)
    errors.Add("Лимит записи не должен быть выше лимита чтения");
```

**Node.js**:
```javascript
if (!Number.isInteger(read) || read <= 0) 
    errors.push("Лимит чтения должен быть больше нуля");
if (Number.isInteger(read) && Number.isInteger(write) && write > read) 
    errors.push("Лимит записи не должен быть выше лимита чтения");
```

**Как это происходит:**
1. При указании `readPerMinute=0` приложение не запустится
2. При указании `writePerMinute > readPerMinute` приложение не запустится
3. Это предотвращает бессмысленные конфигурации

### 3. `Mode` - Режим работы (Учебный/Боевой)

**Почему это критично:**
- Учебный режим раскрывает детали ошибок для диагностики
- Боевой режим скрывает детали для безопасности
- Случайный запуск в учебном режиме на production может раскрыть внутреннюю информацию

**Валидация в коде:**

**Node.js** (`config.js`):
```javascript
const mode = String(app.mode ?? "").toLowerCase();
if (mode !== "учебный" && mode !== "боевой") {
    errors.push("Режим работы задан неверно, допустимы учебный и боевой");
}
```

**Как это происходит:**
1. Если указан неправильный режим, приложение не запустится
2. Администратор получает четкое сообщение об ошибке
3. Это предотвращает неопределённое поведение

## Архитектура раннего обнаружения ошибок

### Процесс запуска (оба проекта)

```
1. Прочитать конфиг из файла
       ↓
2. Перекрыть значения из переменных окружения
       ↓
3. Перекрыть значения из аргументов командной строки
       ↓
4. ВАЛИДИРОВАТЬ все значения
       ↓
   ❌ Если ошибок → Остановить ✓ Если ок → Продолжить
       ↓                              ↓
   Вывести ошибки                 Создать приложение
   в консоль                      с проверенной конфигом
   process.exit(1)
       ↓
   Администратор видит
   проблему до запуска
```

### Почему ранняя валидация критична

#### ✅ Преимущества раннего обнаружения:

1. **Fail-fast**: Проблемы обнаруживаются до того, как приложение попадёт на production
2. **Видимость**: Администратор сразу видит в консоли, что не так
3. **Предсказуемость**: Нет "молчаливых" отказов в процессе работы
4. **Безопасность**: Конфигурационные ошибки не превращаются в уязвимости
5. **Отладка**: Четкие сообщения об ошибках экономят часы диагностики

#### ❌ Если валидация отсутствует:

```
Приложение запускается → Работает с пустым TrustedOrigins → 
Открыто для CORS атак → Взлом → Инцидент безопасности
```

vs.

```
Приложение попыталось запуститься → 
Валидация: "Список доверенных источников пуст" → 
Остановлено → Администратор видит ошибку → Исправляет конфиг → 
Приложение запускается защищённым
```

## Реализация защиты на уровне конфигурации

### Двухслойная защита

**Слой 1 - Валидация конфигурации** (до запуска)
- Проверка, что все критичные параметры установлены
- Проверка, что параметры логически корректны
- Предотвращение запуска при ошибках

**Слой 2 - Защитные механизмы в runtime** (во время работы)

**C#** (`Program.cs`):
```csharp
// Слой 1: Валидация перед запуском
var errors = AppOptionsValidator.Validate(options);
if (errors.Count > 0)
{
    Console.Error.WriteLine("Запуск остановлен...");
    throw new InvalidOperationException("Некорректные настройки приложения");
}

// Слой 2: Применение защиты с проверенной конфигировкой
builder.Services.AddCors(cors =>
{
    cors.AddPolicy("TrustedOrigins", policy =>
    {
        policy.WithOrigins(options.TrustedOrigins)  // ← Гарантированно не пусто
              .AllowAnyHeader()
              .AllowAnyMethod();
    });
});

builder.Services.AddRateLimiter(limiter =>
{
    // Лимиты гарантированно > 0 и логически корректны
    limiter.AddPolicy("read", httpContext =>
        RateLimitPartition.GetFixedWindowLimiter(key,
            _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = options.RateLimits.ReadPerMinute,  // ← Проверено
                Window = TimeSpan.FromMinutes(1),
                QueueLimit = 0
            }
        );
});
```

**Node.js** (`server.js`):
```javascript
// Слой 1: Валидация
const errors = validateConfig(cfg);
if (errors.length > 0) {
    console.error("Запуск остановлен из за некорректных настроек");
    process.exit(1);
}

// Слой 2: Применение защиты с гарантировано проверенной конфигорацией
const limiter = createRateLimiter({ 
    readPerMinute: limits.readPerMinute,  // ← Проверено и > 0
    writePerMinute: limits.writePerMinute // ← Проверено и > 0
});

// CORS применяется только с гарантировано непустым списком
const trustedOrigins = getTrustedOrigins(cfg);  // ← Проверено
applyCors(req, res, trustedOrigins);
```

## Как это снижает риски

### Вектор атаки 1: CORS Bypass

**Без валидации:**
- Администратор забывает установить TrustedOrigins
- Приложение запускается с пустым списком
- Браузер не отправляет CORS заголовки, но SOP уязвима
- Attacker запускает CSRF атаку из своего сайта

**С валидацией:**
- Администратор забывает установить TrustedOrigins
- Приложение НЕ запускается
- Консоль показывает: "Список доверенных источников пуст"
- Администратор видит ошибку и исправляет конфиг перед deployment

### Вектор атаки 2: DoS (Denial of Service)

**Без валидации:**
- ReadPerMinute и WritePerMinute имеют значения по умолчанию
- Если default = 0, нет дросселирования
- Attacker может завалить сервер запросами

**С валидацией:**
- Если указано ReadPerMinute = 0, приложение не запускается
- Сообщение об ошибке: "Лимит чтения должен быть больше нуля"
- Администратор устанавливает разумный лимит (например, 1000)

## Вывод

Раннее обнаружение ошибок конфигурации - это **первая линия защиты** приложения. Это дешевле всего (просто проверка значений), но предотвращает дорогостоящие инциденты безопасности.

**Принцип:** Лучше не запуститься с плохой конфиг, чем запуститься и раскрыть себя для атак.
